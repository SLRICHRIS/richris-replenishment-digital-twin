06

Why the architecture is structured this way

Directly connects the implementation to the methodological lessons of Ferrari et al. (2024).

1. WMS-like task layer

What work is required? A low picking stock level creates a request and reserves physical stock. It does not move stock.

Reason: logical decisions and physical execution must be represented separately.

2. WCS-like execution layer

How is the task executed? Dispatch selects a queued task, checks a traversable path, schedules pickup and delivery, and updates the simulated robot.

Reason: route and resource constraints change execution timing.

3. Event-driven model

When does state change? Only at a recorded time-stamped event: request, dispatch, pickup, delivery or demand.

Reason: every quantity change is explainable and testable.

4. SQLite + API

Where does the state live? A single transactional snapshot and a persistent per-run event log, accessed through HTTP and WebSocket.

Reason: browser reloads must not silently reset the research process.

5. Matched policy experiments

What is the effect of a choice? FIFO and urgency are run independently with identical external demand and warehouse inputs.

Reason: policy comparisons require controlled conditions.

6. Explicit validation boundary

What remains unknown? Equipment times, telemetry calibration and physical-state synchronization still need independent measurement.

Reason: a functioning software model is not proof of a validated Digital Twin.

Reference: Ferrari, A., Carlin, A., Rafele, C., & Zenezini, G. (2024). A method for developing and validating simulation models for automated storage and retrieval system digital twins. The International Journal of Advanced Manufacturing Technology, 131, 5369–5382. DOI: 10.1007/s00170-023-12660-y.
