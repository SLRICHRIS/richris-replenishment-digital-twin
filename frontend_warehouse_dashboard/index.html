    Equation & variables

    Δs = 2πrΔn/N; v = Δs/Δt

    L/R identify the wheels. Δs: travel (m); r: calibrated radius (m); Δn: count increment; N: effective counts per wheel turn, including gearing and quadrature; Δt: device interval (s); v: speed (m/s); π: circle constant.

    Local x / y / θ (m / m / rad)

    Equation & variables

    Δs = (ΔsR + ΔsL)/2; Δθ = (ΔsR − ΔsL)/B
    x′ = x + Δs cos(θ + Δθ/2)
    y′ = y + Δs sin(θ + Δθ/2); θ′ = θ + Δθ

    x/y: position (m); θ: heading (rad); B: wheel separation (m); ΔsL/ΔsR: left/right travel (m); Δs: centre travel (m); Δθ: turn (rad); prime: next sample. Rolling assumption; local frame, no absolute position measurement.

    eω: yaw residual (rad/s); z: gyro rate (rad/s); b̂: bias (rad/s); vL/vR: wheel speeds (m/s); B: track (m); τ: calibrated threshold (rad/s); Thold: required duration (s). Timing begins at the first abnormal sample and resets after a normal, stale or missing sample.

    06 · Motion and runtime forecasts

    5 s forecast x / y / θ
    —
    Runtime to 20% reserve (h)
    —
    Equation & variables

    Repeat midpoint pose update with fixed vL/vR for horizon H in 20 substeps.
    Runtime = max(0, SOC − reserve) C / Ifuture

    H: horizon (s), here 5; Δt = H/20; vL/vR: assumed wheel speeds (m/s); x/y/θ: forecast pose (m/m/rad); SOC/reserve: fractions; C: usable Ah; Ifuture: assumed positive discharge current (A), here latest reading. Runtime is hours; unavailable for non-positive current.

    Where used Paper and PDF page Implementation boundary

    ⓘ Model & measurement boundaries +

    Workflow background: Ferrari et al. (2024), Section 4 — simulation architecture . The replenishment task and inventory workflow is adapted for this project; routing heuristics, battery assumptions and forecasts are project implementations.

    This interactive 3D scene uses the project's single-AMR replenishment workflow. Each robot carries 30 units along simplified aisle routes. Battery drains during motion and recharges at the depot. Shelf inventory decreases at a configured consumption rate. The reference layout has 12 racks: four monitored replenishment stations and eight reserve storage racks. Three cross aisles and four connecting lanes form a shared route graph used by both dispatch and Reference lab defaults. Reserve cartons are decorative and carry no measured inventory. The surrounding cutaway hall adds receiving and dispatch doors, pallet staging, packing and quality benches, service cabinets, structural steel and overhead services. These fixtures are illustrative context outside the 12 × 6.7 m mapped AMR zone; they do not report equipment states or extend the telemetry map. The Facility layer can hide the building and equipment, and Plan view removes the walls and overhead frame for route inspection. Geometry and dimensions are illustrative. Lighting, metal surfaces, concrete and cartons are rendered in real-time 3D. Wheel and payload animation follows simulation state. A simpler compatibility view is used when WebGL 2 is unavailable. AMR-01 completes one virtual journey at a time, including its return to the single middle left-apron bay. Routes are checked against the reference rack footprints with a conservative robot clearance envelope. This is a discrete route model, not physical collision avoidance or a dynamics model.

    The optional cone overlay is illustrative; the component list has no range sensor. Manager circles are manually placed simulation areas, not detected people. The +5s layer projects motion along each assigned route using current speed and pause/stop state. It does not predict interactions or new assignments. Dispatch estimates integrate aisle speed and the complete return journey. A 15% return battery reserve is required. Shortest-distance routing is the default; fastest travel time is a separate objective. Lane closures remove permitted links. Approved outward and return paths are retained, and route settings lock until reserved journeys clear. Battery on return is a conservative minimum before any additional bay charging. Inventory projections use the same chronological approved queue, including charging waits; unapproved deliveries and arrivals behind paused or impossible reservations are excluded. Demand and speed are assumed constant over the forecast window.

    Prediction runs in a separate browser Web Worker. Browser command handling and forecast round-trip timings are diagnostics, not validated physical override latency, Wi-Fi delay or system reliability. In Streamlit, Hardware receives Python-computed results from raw AMR-01 sensors. Live odometry remains in its local frame; a surveyed coordinate transform is required before it can update the 3D floor. Physical accuracy and advisory performance require measured validation. Live data does not drive simulated stock or tasks. This viewer sends no motor commands. LabVIEW, Coordinator/UART control and browser v1 telemetry are legacy references outside the active sensor path. Simulation time pauses while the tab is hidden.
