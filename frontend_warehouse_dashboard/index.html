          How to read readiness

          A connection is one part of the journey.

          Follow the evidence in order: received packet, stored record, valid calibration, recommendation, human decision, controller response, then measured outcome.

          • Sensor archive connectivity does not prove that every model is calibrated.
          • The Logitech browser preview helps with placement. Physical routing uses the laptop program reading that same Logitech webcam.
          • Approve & run applies to one server-reviewed route. Fresh feedback is needed throughout execution.
          • Practice and the illustrative warehouse floor use separate simulation state. Stock events and virtual movement are not physical sensor evidence.
          Data engineering and recovery

          Robot/boot/sequence identity supports deduplication. Schema and availability checks reject invalid observations. Original receive time determines freshness. Full-model writes use a single writer, atomic state/checkpoint updates and calibration fingerprints. Missing intervals stay unknown.

          The commissioning archive is amr_commissioning_samples . The full calibrated path has separate samples, derived states, calibration records and quality events. Human review and physical-route audit records preserve decisions separately.

          What remains before a physical route

          Verify camera lens calibration, four floor references, empty-floor background, marker alignment and the body envelope. Measure motor polarity, PWM response and stopping distance, confirm electrical ratings, and validate obstacle detection. The ESP32 receiver and laptop controller must be running with fresh authenticated evidence.

          Recorded dimensions and successful software tests do not mark these physical checks complete.

            Wheel motion

            Wheel speed

            How it works & source

            Calculated from encoder count changes. Positive travel follows the calibrated forward direction.

            Δs = 2πrΔn/N; v = Δs/Δt

            L/R identify the wheels. Δs: travel (m); r: calibrated radius (m); Δn: count increment; N: effective counts per wheel turn, including gearing and quadrature; Δt: device interval (s); v: speed (m/s); π: circle constant.

            Paper A · p. 11 Eq. (9), p. 38 Eq. (A4)

            WHEEL ODOMETRY

            Position & heading

            Estimated local position
            —

            How it works & source

            x and y are metres from the trial origin; heading is in radians. These coordinates are not registered to the warehouse floor map.

            Δs = (ΔsR + ΔsL)/2; Δθ = (ΔsR − ΔsL)/B
            x′ = x + Δs cos(θ + Δθ/2)
            y′ = y + Δs sin(θ + Δθ/2); θ′ = θ + Δθ

            x/y: position (m); θ: heading (rad); B: wheel separation (m); ΔsL/ΔsR: left/right travel (m); Δs: centre travel (m); Δθ: turn (rad); prime: next sample. Rolling assumption; local frame, no absolute position measurement.

            Paper A · p. 8 Eqs. (1–3) · midpoint adaptation

            MPU6050

            Gyro bias correction

            Raw yaw rate (rad/s)
            —
            Calibrated stationary bias (rad/s)
            —
            Corrected yaw rate (rad/s)
            —

            How it works & source

            Subtract the stationary bias from the measured turning rate. The corrected gyro checks wheel motion; position still comes from wheel odometry.

            z = ω + b + ν; b̂ = mean(stationary z); ω̂ = z − b̂

            z: measured yaw rate; ω: true yaw rate; b: bias; ν: noise; b̂: estimated stationary bias; ω̂: bias-corrected rate. All rates in rad/s. Bias correction still leaves noise; heading is wheel odometry. No EKF is added.

            Paper A · p. 10 Eq. (8)

            INA219

            Battery state

            Estimated charge (SOC)
            —
            Measured battery input
            —
            Electrical power (W)
            —
            Net energy used (Wh)
            —

            How it works & source

            SOC means state of charge. Positive current means discharge; negative current means charging. Charge and net energy are calculated estimates.

            P = VI; E′ = E + VIΔt/3600
            SOC′ = SOC − IΔt/(3600 C)

            V: pack voltage (V); I: discharge-positive current (A); P: power (W); E: net energy used (Wh); Δt: interval (s); C: usable capacity (Ah); SOC: charge fraction; prime: next sample; 3600: seconds/hour. Initial SOC/capacity must be measured; efficiency is 1.

            The physical-feed charge scenario uses the reported 2.2 Ah capacity and assumes 100% at the first stored battery sample of the boot. It integrates recorded motor-branch current by the trapezoidal rule; gaps and other loads are omitted. This does not establish actual battery charge. Values outside 0–100% expose an inconsistent starting assumption or current input and are not silently clipped.

            Paper B · pp. 7–8 Eqs. (5–9) · adapted sign; P/Wh use standard definitions

            Short-term forecast

            Estimated position in 5 seconds

            Time until 20% charge

            Assumes unchanged wheel speeds and battery current. This is not a planned route or a battery-life guarantee.

            How it works & source

            Repeat midpoint pose update with fixed vL/vR for horizon H in 20 substeps.
            Runtime = max(0, SOC − reserve) C / Ifuture

            H: horizon (s), here 5; Δt = H/20; vL/vR: assumed wheel speeds (m/s); x/y/θ: forecast pose (m/m/rad); SOC/reserve: fractions; C: usable Ah; Ifuture: assumed positive discharge current (A), here latest reading. Runtime is hours; unavailable for non-positive current.

            The physical-feed pack scenario substitutes the reported starting charge and nominal capacity. It describes a hypothetical discharge at the latest motor-branch current, not the battery's actual remaining runtime.

                Workflow background: Ferrari et al. (2024), Section 4 — simulation architecture . The replenishment task and inventory workflow is adapted for this project; routing heuristics, battery assumptions and forecasts are project implementations.

                This interactive 3D scene uses the project's single-AMR replenishment workflow. AMR-01 carries 30 units along simplified aisle routes. Battery drains during motion and recharges at the depot. Shelf inventory decreases at a configured consumption rate. The reference layout has 12 racks: four monitored replenishment stations and eight reserve storage racks. Three cross aisles and four connecting lanes form a shared route graph for virtual dispatch. Reserve cartons are decorative and carry no measured inventory. The surrounding cutaway hall adds receiving and dispatch doors, pallet staging, packing and quality benches, service cabinets, structural steel and overhead services. These fixtures are illustrative context outside the 12 × 6.7 m mapped AMR zone; they do not report equipment states or extend the telemetry map. The Facility layer can hide the building and equipment, and Plan view removes the walls and overhead frame for route inspection. Geometry and dimensions are illustrative. Lighting, metal surfaces, concrete and cartons are rendered in real-time 3D. Wheel and payload animation follows simulation state. A simpler compatibility view is used when WebGL 2 is unavailable. AMR-01 completes one virtual journey at a time, including its return to the single middle left-apron bay. Routes are checked against the reference rack footprints with a conservative robot clearance envelope. This is a discrete route model, not physical collision avoidance or a dynamics model.

                The optional cone overlay is illustrative; the component list has no range sensor. Manager circles are manually placed simulation areas, not detected people. The +5s layer projects motion along each assigned route using current speed and pause/stop state. It does not predict interactions or new assignments. Dispatch estimates integrate aisle speed and the complete return journey. A 15% return battery reserve is required. Shortest-distance routing is the default; fastest travel time is a separate objective. Lane closures remove permitted links. Approved outward and return paths are retained, and route settings lock until reserved journeys clear. Battery on return is a conservative minimum before any additional bay charging. Inventory projections use the same chronological approved queue, including charging waits; unapproved deliveries and arrivals behind paused or impossible reservations are excluded. Demand and speed are assumed constant over the forecast window.

                Prediction runs in a separate browser Web Worker. Browser command handling and forecast round-trip timings are diagnostics, not validated physical override latency, Wi-Fi delay or system reliability. Sensor models receives Python-computed results from raw AMR-01 sensors. Live odometry remains in its local frame; a surveyed coordinate transform is required before it can update the 3D floor. Physical accuracy and advisory performance require measured validation. Live data does not drive simulated stock or tasks. Website review passes decisions to the protected Python service; physical command delivery remains disabled until receiver commissioning. Coordinator/UART control and browser telemetry are legacy references outside the active sensor path. Simulation time pauses while the tab is hidden.
